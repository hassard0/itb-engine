# v2.62 - GW parity native packet registry: source-ready, non-promoting

## Question

v2.61 showed that public GW parity likelihood material exists, but not in the
engine `g_R2_parity` / `g_R3_parity` basis. This iteration adds a native packet
schema and registry so those sources can be tracked without promoting them as
engine-axis measurements.

## Implementation

New reusable guard:

```text
src/itb/gw_parity.py
```

It defines:

- `GWParityNativePacket`
- `validate_gw_parity_native_packet`

The guard separates:

- native source readiness: source URL, allowed native basis, required native
  parameters, public code/data/likelihood material;
- engine projection readiness: source-backed operator map, dimensional
  conversion, frequency normalization, framework-exclusion math, and explicit
  `engine_projection_ready` status.

## Registered Packets

| packet | native basis | source ready? | engine projection ready? |
|---|---|---:|---:|
| `ng_gwtc3_kappa_at_100hz` | `ng_kappa_at_100hz` | yes | no |
| `callister_sgwb_kappaD_kappaz` | `sgwb_kappaD_kappaz` | yes | no |

The Ng packet preserves the native `kappa = -0.019^{+0.038}_{-0.029} Gpc^-1`
at 100 Hz and `M_PV > 6.8e-21 GeV`. The Callister packet preserves the native
`kappa_D` / `kappa_z` SGWB basis as an order-0.1 joint-bound scale.

## Blockers

Both packets remain blocked by:

- `missing_source_backed_operator_map`
- `missing_dimensionful_to_engine_normalization`
- `missing_frequency_normalization`
- `missing_framework_exclusion_math`
- `engine_projection_not_ready`

## Interpretation

This is a useful engineering step, not a physics claim. The engine can now carry
public GW parity evidence in its native basis without confusing it with a
`g_R2_parity` / `g_R3_parity` likelihood. The next useful artifact is a
PPV/native-basis adapter specification that maps Ng `kappa` and Callister
`kappa_D` / `kappa_z` into a shared source-backed propagation basis, still
without engine-axis promotion.

No quantum-gravity solution claim is available from this registry.
