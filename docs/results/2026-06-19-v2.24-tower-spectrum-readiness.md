**Date:** 2026-06-19

## Question

v2.23 identified which tower measurements would reduce assignment ambiguity. v2.24 asks:

> Can any current framework encoder supply the missing framework-specific tower spectrum?

The answer is no. The current framework layer predicts Wilson coefficients, but no
framework exposes a normalized tower spectrum with uncertainty. Therefore the engine
must continue to report zero claimable framework-level tower exclusions.

## Result

Default readiness counts:

```json
{
  "n_native_prediction_frameworks": 0,
  "n_actionable_prediction_frameworks": 0,
  "claimable_framework_exclusions": []
}
```

Every framework has the same default verdict:

```json
{
  "framework_tower_verdict": "missing_actionable_tower_spectrum",
  "missing_fields": [
    "tower_family",
    "phi_tower_mean",
    "phi_tower_sigma",
    "normalization",
    "source"
  ]
}
```

The required adapter contract is:

| field | purpose |
|---|---|
| `tower_family` | names the spectrum family, such as KK, string oscillator, species, or model-specific |
| `phi_tower_mean` | dimensionless tower coordinate in the v2.20 normalization |
| `phi_tower_sigma` | one-sigma uncertainty in the same normalization |
| `tower_mass_gap` | optional mass-gap input, converted to `phi_tower` if `phi_tower_mean` is absent |
| `normalization` | explains how the framework maps its physical scale into `m0/lambda_tower` units |
| `source` | cites the literature, data product, or generator that justifies the spectrum |

## Guardrail

The tests include a synthetic adapter fixture to prove the wiring works: a future
framework prediction with a two-sigma `phi_tower` interval fully above the critical
value produces `tower_excluded_by_predictive_spectrum`.

That fixture is not included as a default artifact claim. The default artifact contains
no native predictions and no framework exclusions.

## Interpretation

v2.24 turns the v2.23 bottleneck into an explicit engineering contract. `Framework`
now has a non-abstract `tower_spectrum()` hook that defaults to `None`, backed by a
small `TowerSpectrum` dataclass. This is useful because it prevents the next loop from
accidentally treating coefficient-derived proxies as tower spectra, while avoiding any
change to the existing Wilson-coefficient feasibility checks.

The defensible claim is:

> The engine is ready to consume framework-level tower spectra, but no current framework
> supplies one. Quantum-gravity discrimination through the tower axis is therefore blocked
> on sourced, normalized spectra, not on the tower gate implementation.

## Code changes

- `src/itb/tower.py` adds the `TowerSpectrum` adapter dataclass.
- `src/itb/frameworks/base.py` adds a default `tower_spectrum() -> TowerSpectrum | None`
  hook.
- `experiments/tower_spectrum_readiness.py` adds a readiness audit and optional spectra
  adapter path.
- `tests/test_framework_tower_spectrum.py` verifies the default hook and typed adapter
  serialization.
- `tests/test_tower_spectrum_readiness.py` verifies that default frameworks produce no
  tower claims and that a synthetic adapter can drive the verdict logic.
- `experiments/results/v2.24/tower_spectrum_readiness.json` stores the verified artifact.

## Bottom line

The next real research step is to populate this adapter for at least one framework from
a sourced tower spectrum. Until then, v2.20-v2.24 support measurement design and wiring,
but not a solved framework-level quantum-gravity exclusion.
