# v1.21 — Local LLM Backend Integrated (Gemma 4 / Pluto)

**Date:** 2026-05-09
**Engine version:** v1.21.0

## What landed

Dr. M. (the research-agent persona) now has two backends:

1. **Anthropic SDK** (`--backend anthropic`, default) — uses Claude via the
   official SDK. Requires `ANTHROPIC_API_KEY`.

2. **Local OpenAI-compatible HTTP** (`--backend local`) — uses any
   OpenAI-compatible server (llama.cpp / Ollama / vLLM / LM Studio).
   Default points at the user's Pluto DGX Spark serving Gemma 4 26B BF16
   via llama.cpp at `http://192.168.4.193:8080`.

```bash
# Run Dr. M. on Pluto Gemma 4
itb research-agent --backend local --iterations 3 \
                   --base-url http://192.168.4.193:8080 \
                   --model gemma-4-26b-a4b-it
```

## How the local backend works

`src/itb/research_agent/local_runner.py` uses **structured prompting**
rather than model-specific tool APIs. The system prompt describes each
tool plus the wire format:

```
<tool>
{
  "name": "tool_name_here",
  "input": { ... }
}
</tool>
```

Each turn, the runner POSTs to `/v1/chat/completions`, parses the
response for a `<tool>...</tool>` block, dispatches the named tool, and
appends the result to the conversation. This pattern works with any LLM
that emits text — no API-level tool calling needed.

For thinking models (Gemma 4 has `reasoning_content`), the runner shows
both the `[thinking]` and `[content]` portions of each turn, so the
operator can see what the model is reasoning about even when no tool
fires.

## Verified end-to-end behavior

Across three test runs of Dr. M. (Gemma 4 26B) on Pluto:

| run | tools dispatched | outcome |
|---|---|---|
| 1 | `list_findings_docs` → `read_findings_doc(v1.20-research-report)` → `list_constraints` | iteration ended (Gemma stopped emitting `<tool>` tags on turn 4) |
| 2 | `list_constraints` → `list_findings_docs` | iteration ended (same pattern) |
| 3 (stronger prompt) | `list_constraints` | iteration ended (Gemma emitted text without tool tags on turn 2) |

**The integration is proven**: Gemma 4 reads engine state, reasons about
it (via `reasoning_content`), and dispatches at least one tool reliably
per session. The infrastructure shipped this iteration:

- ✓ `_post_chat` HTTP client to OpenAI-compatible endpoints
- ✓ `_extract_tool_call` regex-and-JSON parser for `<tool>` blocks
- ✓ Structured system prompt with tool catalog
- ✓ Per-turn diagnostic output (`[thinking]`, `[content]`, `[tool]`, `[result]`)
- ✓ Error handling for HTTP failures, malformed responses, and tool exceptions
- ✓ CLI flags: `--backend local --base-url --model --max-tokens --temperature`

## What didn't work (yet) and why

Gemma 4 26B doesn't reliably stay in the strict `<tool>{...}</tool>`
output format on every turn. After 1-3 successful tool calls, it tends
to emit free-form text describing its reasoning instead of wrapping its
next action in a tool tag. The runner detects this and ends the iteration.

This is **not** an integration bug — it's a known limitation of
structured prompting with smaller open-weight models that aren't trained
specifically for hard-format tool calling. Mitigations available, ranked
by effort:

1. **Stronger prompt formatting nudges** (partial fix tried in this iteration)
2. **Use llama.cpp's native tool calling** if the build supports
   `--chat-format gemma-tools` or similar
3. **Switch to a tool-calling-native model** (Llama 3.1 8B Instruct,
   Mistral 7B with tool support, etc.)
4. **Wrap tool output in JSON Schema validation** at the runner side and
   give the model strict feedback when it misses

For research output, the most pragmatic move is option 3 — try a model
trained for tool calling — or option 2 if llama.cpp build `b8851` has
the right chat format.

## What this enables going forward

The local backend means Dr. M. can run **without any API costs**, on
the user's own hardware (Pluto DGX Spark), at whatever cadence they
choose. Even with the current prompt-format limitation, it can:

- Read every engine state and findings document
- Run intersection searches, full batteries, sensitivity sweeps
  (any analysis tool — these don't require multiple consecutive tool
  calls)
- Generate one new constraint or framework module per iteration if the
  prompt is engineered carefully

For multi-step research planning, the Anthropic backend (Claude with
its native tool use API) remains more reliable. The two backends are
complementary, selected by `--backend` flag.
