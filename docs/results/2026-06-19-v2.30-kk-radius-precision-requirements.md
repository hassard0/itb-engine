## Question

v2.29 gave radius-ratio thresholds at fixed uncertainty. v2.30 asks the inverse question:

> Given a sourced central `R/R0`, how small must `log_radius_sigma` be before the tower
> verdict is claimable?

This turns the KK-radius adapter into a measurement-design requirement.

## Rule

The critical radius ratio is:

```json
{
  "critical_phi_tower": 0.7433019116911739,
  "critical_radius_ratio": 2.102867546654528
}
```

For `phi_mean = log(R/R0)`:

- if `R/R0` is below the critical ratio, allowance requires
  `log_radius_sigma <= (critical_phi - phi_mean) / 2`;
- if `R/R0` is above the critical ratio, exclusion requires
  `log_radius_sigma < (phi_mean - critical_phi) / 2`;
- exactly at the boundary, only zero uncertainty reaches the allowance boundary.

## Interpretation

v2.30 makes the KK-radius route operational as an experimental or compactification target.
The farther the sourced radius ratio sits from the critical ratio, the looser the allowed
uncertainty. Near the critical ratio, the radius measurement must be very precise or the
two-sigma interval overlaps the tower threshold.

The defensible claim is:

> The engine can now state the precision a sourced KK-radius adapter must achieve, but no
> registered framework supplies such a sourced radius. There are still no framework-level
> tower exclusions.

## Code changes

- `experiments/kk_radius_precision_requirements.py` computes inverse precision
  requirements for KK-radius adapters.
- `tests/test_kk_radius_precision_requirements.py` verifies both sides of the threshold,
  verdict checks at explicit uncertainties, and boundary classification.
- `experiments/results/v2.30/kk_radius_precision_requirements.json` stores the verified
  artifact.

## Bottom line

The missing input is now not just `R/R0`; it is `R/R0` with enough log-radius precision to
place the two-sigma interval entirely on one side of `R/R0 = 2.1029`.
