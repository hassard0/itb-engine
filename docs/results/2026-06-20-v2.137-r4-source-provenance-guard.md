# v2.137 - R4 source-provenance guard blocks nested fixtures

## Question

v2.136 proved that `c_plus/c_minus` coordinates can be inverted into
Bresciani `g_R4_c1/c2/c3` axes and passed through the algebraic R4 projection
guard. But the v2.136 fixture marked itself synthetic inside
`ownership_metadata`, while the v2.133 guard only rejected a top-level
`synthetic_fixture = true`.

Can the engine keep the algebraic projection guard usable while adding a strict
source-provenance overlay that rejects nested synthetic fixtures before any
future R4 adapter is treated as source-backed?

## Strict Provenance Contract

The overlay composes the v2.133 algebraic/schema guard with explicit source
provenance:

```text
source_backed_derivation
derivation_kind
primary_source_urls
synthetic_fixture
```

Accepted derivation kinds:

```text
primary_source_derivation
published_framework_projection
validated_public_reanalysis
```

The packet source URL must be listed in `source_provenance.primary_source_urls`,
all source URLs must be arXiv or DOI primary-source URLs, and no truthy
`synthetic_fixture` key may appear anywhere in the packet.

## Controls

The source-backed control packet passes strict projection readiness:

```text
base_ready_for_framework_projection = true
ready_for_source_backed_framework_projection = true
strict_projection_blockers = []
```

It remains non-claiming:

```text
ready_for_framework_claim = false
strict_claim_blockers = [
  discriminator_math_not_excluding,
  measurement_likelihood_missing_or_incomplete
]
```

The v2.136 fixture replay still passes the base algebraic guard:

```text
base_ready_for_framework_projection = true
```

But it is blocked by strict source provenance:

```text
ready_for_source_backed_framework_projection = false
strict_projection_blockers = [
  source_provenance_missing_or_incomplete,
  synthetic_fixture_not_real_source
]
```

The detected nested marker is explicit:

```text
$.ownership_metadata.synthetic_fixture
```

## Interpretation

This keeps the v2.136 coordinate fixture useful as a contract test while
preventing it from being promoted as source-backed R4 physics. Future R4
adapters must provide `source_provenance`, must list the same primary source URL
used by the packet, and must have no synthetic-fixture markers anywhere in the
packet before they can be treated as source-backed framework projections.
