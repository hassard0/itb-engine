# v2.45 - Generic framework claim guard: promotion-ready is not claim-ready

**Date:** 2026-06-19
**Compute:** local run
**Input:** v2.34, v2.37, v2.38, v2.41, and v2.44 candidate evidence rows
**Artifacts:**

- `experiments/results/v2.45/generic_framework_claim_guard_audit.json`
- `experiments/results/v2.45/discriminator_frontier_status_matrix.json`

## Question

v2.44 classified source scope separately from the positive-control promotion
guard. v2.45 asks:

> Can the engine enforce that distinction before any framework-level quantum
> gravity exclusion is marked claim-ready?

Yes. `src/itb/tower.py` now exposes
`evaluate_generic_framework_claim_guard(evidence, tower_claimable_by_math=...)`.
This guard requires:

- schema-ready `TowerEvidence`
- excluding tower math
- no known positive-control family
- explicit asymptotic source scope
- truthy framework-owned endpoint metadata
- truthy framework-owned displacement metadata

## Code Changes

- `evaluate_generic_framework_claim_guard(...)` composes the existing
  promotion guard with source-scope readiness.
- `classify_tower_source_scope(...)` now treats ownership as structured truthy
  metadata, not accidental string-token presence.
- `classify_discriminator_frontier_status(...)` has a distinct
  `tower_generic_claim_guard_blocked` branch.
- The branch matrix now separates promotion-guard blocking from generic-claim
  blocking.
