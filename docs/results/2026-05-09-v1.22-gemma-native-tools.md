# v1.22 — Gemma 4 native tool calling on Pluto

**Date:** 2026-05-09
**Engine version:** v1.22.0
**Hardware:** Pluto DGX Spark (192.168.4.193), llama.cpp build `b8851-e365e658f`, model `gemma-4-26b-a4b-it`

## What landed

The local-LLM research-agent backend now uses **native OpenAI-compatible
tool calling** when the server supports it. Probing Pluto's `/props`
endpoint confirmed Gemma 4's chat template advertises:

```json
{
  "supports_tool_calls": true,
  "supports_tools": true,
  "supports_object_arguments": true,
  "supports_parallel_tool_calls": true,
  "supports_preserve_reasoning": true
}
```

`itb research-agent --backend local` now auto-detects this and uses the
`tools` parameter on `/v1/chat/completions` rather than the
`<tool>{...}</tool>` structured-prompt fallback. The result format is
the OpenAI standard `message.tool_calls[]` array, with proper
`{id, function: {name, arguments}}` shape.

## End-to-end verification

Running `itb research-agent --backend local --iterations 2 --max-tokens 8000`
against Pluto produced the following trajectory:

| step | tool | finish_reason | prompt_tokens | completion_tokens |
|---|---|---|---|---|
| 1 | `list_constraints` | `tool_calls` | 1893 | 348 |
| 2 | `compute_intersection` | `tool_calls` | 3206 | 1976 |
| 3 | `read_findings_doc` (v1.14) | `tool_calls` | (continuing...) | (continuing...) |

Notably:

- `finish_reason: tool_calls` is the OpenAI signal that the model
  finished by emitting a structured tool call (no format-drift possible)
- `tool_calls=1` per step (parallel-tool-calls supported but Gemma
  emitted serial calls)
- `compute_intersection` returned the expected v1.8/v1.10 optimum:
  `g_4≈0.622, g_6≈0.395, g_R²≈0.233, parity≈0`, worst-case margin
  `+0.00868`
- All tool calls dispatched cleanly through the existing tool registry

## Why this matters

The structured-prompt approach (v1.21) reliably worked for the first
1-3 tool calls of an iteration but Gemma 4 would drop format on later
turns, ending the iteration. With native tool calling at the API
level, **format drift is impossible** — llama.cpp itself enforces the
tool call shape, and the model's reasoning_content is preserved
separately from the structured tool output.

## Performance characteristics

Gemma 4 26B BF16 on Pluto generates at ~21 tokens/second per slot. A
typical Dr. M. turn uses 1500-2500 completion tokens (mostly in
`reasoning_content`), so each turn is ~70-120 seconds wall-clock. An
8-step iteration is ~10-15 minutes; a 2-iteration session is ~20-30
minutes. This is real-time enough for interactive research-agent
loops, but slow for batch-style sweeping.

## Remaining limitations

- **Speed.** 21 tok/sec is the slot limit. Multiple parallel slots
  would help; running a smaller (4B/8B) tool-calling model would help
  more.
- **Single-iteration tool depth.** Gemma uses ~2000 thinking tokens per
  turn even for simple reads, eating into the available step budget.
  Could be tuned with prompt nudges to think less.
- **No code-generation tested yet.** `propose_new_module` requires
  Gemma to emit valid Python source through `arguments` JSON. The
  test runs so far have all been read-only and analysis tools; the
  full "Dr. M. proposes a new constraint module via Gemma" loop is
  ready to test but hasn't completed end-to-end yet.

## Architecture summary

```
itb research-agent --backend local
  → run_local_agent(base_url, model, ...)
    → _supports_native_tools(base_url) probes /props
      → detects supports_tool_calls=true on Pluto
    → _run_with_native_tools(...)
      → POST /v1/chat/completions with tools=[...]
      → parse message.tool_calls (id, function.name, function.arguments)
      → dispatch via existing tools.dispatch() registry
      → append role="tool" message with tool_call_id + content
      → loop until mark_iteration_complete or max_steps_per_iteration
```

The same `dispatch()` registry from `itb.research_agent.tools` is used
across both Anthropic and local backends — only the API-level message
plumbing differs.
