## Guard Split

The guard separates two claims:

```text
ready_for_framework_projection
ready_for_framework_claim
```

`ready_for_framework_projection` requires a complete source-owned R4 projection:

```text
framework registered in itb.predict.FRAMEWORKS
axis_family = gravity_R4_Riemann4
adapter_kind = framework_native_r4_projection
basis = Bresciani_c_i_spin2_Riemann4
source_url from arXiv or DOI
source_type allowed
g_R4_c1, g_R4_c2, g_R4_c3 numeric
g_R4_plus and g_R4_minus_abs consistent with the coefficients
c1 >= 0, c2 >= 0, c3^2 <= 4*c1*c2
source-backed normalization
source-backed operator projection matrix
bounded EFT energy domain
uncertainty or covariance covering all three axes
framework-owned derivation metadata
source-backed Bresciani spin-2 unitarity bound
```

`ready_for_framework_claim` additionally requires:

```text
measurement_likelihood covering the R4 axes
discriminator_math = excludes_registered_framework
```

This matters because a complete framework projection is not the same as a
measurement-backed exclusion.

## Interpretation

The R4 route now has a hard acceptance harness. Future work can add a proposed
R4 adapter without ambiguity: if it lacks coefficients, Bresciani-derived
coordinates, source metadata, normalization, uncertainty, ownership, or bounded
domain, the guard rejects it. Even a complete projection still cannot create a
framework claim without measurement likelihood and excluding discriminator math.
