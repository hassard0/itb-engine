# v2.41 - Tower promotion guard: positive controls blocked before claims

**Date:** 2026-06-19
**Compute:** local run plus fresh Vulcan clone `~/codex-runs/itb-engine-main-v241a`
**Input:** v2.37 large-volume benchmark, v2.38 analytic KK benchmark, and v2.40 recalibration options
**Artifact:** `experiments/results/v2.41/tower_promotion_guard_audit.json`

## Question

v2.40 recommended adding a promotion guard before changing tower-gate math. v2.41 asks:

> Does the guard block known string-compatible positive controls while still allowing a
> non-positive-control excluding row to pass the guard?

Yes.

## Implementation

`src/itb/tower.py` now exposes:

- `tower_positive_control_matches(evidence)`
- `evaluate_tower_promotion_guard(evidence, tower_claimable_by_math=...)`

`experiments/discriminator_frontier.py` now consults the promotion guard before any row
can become `tower_discriminator_claim_ready`.

## Result

```json
{
  "registered_framework_count": 13,
  "candidate_count": 8,
  "positive_control_promotion_blocked": 7,
  "promotion_guard_ready_non_positive_control_fixtures": [
    "non_positive_control_excluding_fixture"
  ],
  "tower_discriminator_candidates_now": [],
  "claimable_framework_exclusions_now": []
}
```

The seven blocked rows are:

- the large-volume Calabi-Yau benchmark from v2.37
- the six analytic KK decompactification vectors from v2.38

The non-positive-control row is synthetic and therefore not claimable, but it proves the
guard is scoped: it does not simply block every mathematically excluding tower row.

## Bottom line

The engine now has an explicit promotion guard for the positive-control failure found in
v2.39. Tower math remains useful as a diagnostic, but known string-compatible
decompactification controls cannot be promoted into framework exclusions.
